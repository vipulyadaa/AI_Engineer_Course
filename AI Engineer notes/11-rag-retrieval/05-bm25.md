# BM25

> **Phase 11 · RAG RETRIEVAL · Topic 05**

## 1. Definition

A lexical ranking function that scores documents by term frequency, inverse document frequency, and document length normalization. It's decades old, extremely fast, and still the strongest simple keyword baseline — which is why it's the sparse half of hybrid retrieval.

## 2. Simple Explanation

BM25 ranks documents by how well their words match the query's words, with three sensible adjustments:

1. A query term appearing **more often** in a document is a stronger signal — but with diminishing returns.
2. A term that's **rare across the corpus** is more informative than a common one.
3. A **shorter document** containing the term is a better match than a long one that mentions it once.

That's it. No embeddings, no model, no training.

## 3. How It Works

```
                     f(q,d) · (k₁ + 1)
BM25(q,d) = Σ IDF(q) · ─────────────────────────────────
            q∈Q         f(q,d) + k₁ · (1 - b + b · |d|/avgdl)

f(q,d)  = frequency of term q in document d
|d|     = document length,  avgdl = average document length
k₁ ≈ 1.2-2.0  controls term-frequency saturation
b  ≈ 0.75     controls length normalization strength
```

**The three components:**

| Component | Effect |
|---|---|
| **IDF** | Rare terms score higher. "the" contributes nothing; "AC-4471-B" contributes a lot |
| **TF saturation (`k₁`)** | 10 occurrences isn't 10× better than 1 — the curve flattens |
| **Length normalization (`b`)** | Prevents long documents winning simply by containing more words |

**The analysis chain matters as much as the formula:** tokenization, lowercasing, stemming, and stopword removal must be **identical at index time and query time**, or matches silently fail.

## 4. Practical Example

**Where BM25 wins decisively:**

```
Query: "error code E-3021"

BM25:  "E-3021" has very high IDF — it appears in exactly one
       document in the corpus. That document scores overwhelmingly.
       → correct chunk, rank 1.

Dense: The embedding encodes "an error code identifier."
       E-3021, E-3019, and E-4102 all land in nearly the same
       region. The specific one isn't distinguished.
       → correct chunk might be rank 15.
```

**Where BM25 fails:**

```
Query: "what if my transfer bounces"
Document: "If a wire transfer is rejected by the beneficiary bank,
           funds are returned within 5-7 business days."

Shared terms: "transfer" only.
"bounces" ↔ "rejected" — BM25 has no idea these relate.
→ poor ranking despite being the correct answer.
```

**The analysis-mismatch bug:**

```
Index time:  stemming ON   → "transfers" indexed as "transfer"
Query time:  stemming OFF  → searching for "transfers"

→ No match. The document is in the index and unfindable.
   No error. Silent failure.
```

Always verify the analyzer is identical on both sides.

## 5. Why It Matters

- **It's the sparse half of hybrid retrieval**, which is the production default.
- **It handles exactly what dense retrieval can't** — identifiers, codes, rare proper nouns, exact phrases.
- **It's free** — no model, no GPU, no embedding cost, sub-millisecond search on an inverted index.

## 6. Trade-offs / Failure Modes

| Failure | Detail |
|---|---|
| **No semantic understanding** | Synonyms, paraphrase, and related concepts are invisible |
| **Vocabulary mismatch** | User says "overdraft," document says "insufficient funds" |
| **Analyzer mismatch** | Different tokenization or stemming at index vs. query time → silent misses |
| **Stopword removal edge cases** | "to be or not to be" becomes empty after stopword removal |
| **Morphology in other languages** | Stemming rules are language-specific; German compounds and Arabic morphology need special handling |
| **Long documents disadvantaged** | Length normalization helps, but `b` needs tuning per corpus |

**Query expansion is the standard mitigation** for the vocabulary gap — adding synonyms so BM25 has more ways to match. A curated domain synonym map is usually better than LLM expansion here, because the vocabulary is stable and enumerable.

**Tuning `k₁` and `b`:** defaults of 1.2 and 0.75 work well and rarely need changing. If your documents vary enormously in length, lowering `b` reduces the length penalty. It's a much smaller lever than getting the analyzer right.

## 8. Likely Follow-ups

**Q: What do k₁ and b control?**
`k₁` controls term-frequency saturation — how quickly the benefit of additional occurrences flattens out, typically 1.2 to 2.0. `b` controls length normalization strength, typically 0.75, where 0 means no length penalty and 1 means full normalization. The defaults work well; getting the analyzer right matters far more than tuning these.

**Q: Why is BM25 still used when embeddings exist?**
Because it does something embeddings can't: exact token matching. Identifiers, error codes, regulation citations, product SKUs, and rare proper nouns are common in enterprise queries and dense retrieval handles them poorly. It's also free — no model, no GPU, no embedding cost — and sub-millisecond. Hybrid uses both because neither is sufficient alone.

**Q: What is IDF and why does it matter?**
Inverse document frequency weights terms by rarity — a term appearing in one document out of a million is highly informative, while one appearing in every document contributes nothing. It's what makes BM25 work on identifiers: the specificity of a rare token is exactly what IDF rewards, and it's exactly what dense embeddings blur away.

**Q: How do you handle the vocabulary gap?**
Query expansion — adding synonyms and related terms so BM25 has more ways to match. A curated domain synonym map is usually better than LLM-generated expansion, because enterprise vocabulary is stable and enumerable and a domain expert knows that overdraft, NSF, and insufficient funds are the same concept. The other mitigation is simply running dense retrieval alongside, which is what hybrid does.

**Q: What's the most common BM25 bug?**
Analyzer mismatch between index time and query time — different tokenization, stemming, or stopword lists. It produces silent misses: the document is indexed and the query can't find it, with no error anywhere. I'd verify by indexing a known document and querying for a term I know is in it, as a smoke test after any configuration change.

## 9. Common Mistakes

- Different analysis chains at index time and query time.
- Expecting BM25 to handle synonyms or paraphrase.
- Tuning k₁ and b before verifying the analyzer is correct.
- Removing stopwords without considering queries that are mostly stopwords.
- Applying English stemming rules to other languages.

## 10. What to Remember

- **TF × IDF with saturation and length normalization.** No model, no training, sub-millisecond.
- **It wins on exact identifiers** — high IDF makes a rare token decisive.
- **It fails on paraphrase** — no semantic understanding at all.
- **Identical analysis at index and query time**, or matches fail silently.
- **Defaults k₁=1.2, b=0.75 are fine.** The analyzer matters far more.
