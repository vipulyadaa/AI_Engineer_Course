# Chroma

> **Phase 07 · VECTOR DATABASES · Topic 21**

## 1. Definition

An open-source, developer-focused vector database designed for ease of use. It runs embedded in a Python process or as a lightweight server, and is the common default for prototypes, notebooks, and local development.

## 2. Simple Explanation

Chroma is the one you `pip install` and have working in three lines. It handles embedding, storage, and search with sensible defaults and no configuration.

That's its whole value: getting from nothing to working retrieval fast. It's not built for large corpora or high-concurrency serving.

## 3. How It Works

```python
import chromadb

client = chromadb.PersistentClient(path="./chroma")
col = client.get_or_create_collection("policies")

col.add(                                  # embeds for you if you
    ids=["c1", "c2"],                     # don't pass embeddings
    documents=["Wire fee is $45...", "..."],
    metadatas=[{"doc_type": "policy"}, {...}],
)

col.query(query_texts=["wire transfer fee"],
          n_results=5,
          where={"doc_type": "policy"})
```

**Notable properties:**

```
· Embeds documents automatically with a default model
· Metadata filtering with a where clause
· Persists to local disk; also runs as a server
· HNSW under the hood
· Effectively zero configuration
```

## 4. Practical Example

**Where Chroma is the right choice:**

```
1. LEARNING and PROTOTYPING
   Testing whether a chunking strategy or prompt works before
   committing to infrastructure.

2. NOTEBOOK and LOCAL DEV
   A local index over a sample corpus, no service to run.

3. TESTS
   An in-memory collection makes retrieval tests fast and
   hermetic — genuinely useful in a production codebase.

4. SMALL INTERNAL TOOLS
   A few thousand documents, a handful of users.
```

**The trap: auto-embedding hides the model.**

```
col.add(documents=[...])     # which model embedded this?

The default is a small sentence-transformers model. Convenient
for a demo, but it means:

  · prototype quality doesn't predict production quality
  · a comparison of chunking strategies measured on the default
    model may not hold with text-embedding-005
  · the embedding model — the component that most determines
    retrieval quality — was chosen by a default

I'd pass embeddings explicitly, generated by the same model
production will use, even in a prototype. Otherwise the
prototype measures a different system.
```

**That's the point worth making**, because it's the difference between a prototype that informs the production design and one that doesn't.

**Where it stops:**

```
· Concurrency and multi-writer serving
· Corpora beyond roughly a million vectors
· Replication, backup, and HA
· Fine-grained access control
· Operational tooling and observability
```

## 5. Why It Matters

- **It's the fastest path from idea to working retrieval**, which has real value early.
- **Auto-embedding hiding the model** is the specific trap that invalidates prototype results.
- **In-memory collections make retrieval tests hermetic** — a genuine production use.

## 6. Trade-offs / Failure Modes

| Issue | Detail |
|---|---|
| **Auto-embedding with a default model** | Prototype results don't transfer |
| **Not built for concurrency** | Multi-writer serving is unreliable |
| **Scale limits** | Degrades well before a serious corpus |
| **No replication or HA** | Not a production serving story |
| **Limited access control** | No real multi-tenancy model |
| **Prototype drifting into production** | The common organizational failure |

**On the last row:** the realistic risk isn't that Chroma is bad — it's that a prototype works, gets demoed, and then quietly becomes the system. The defence is architectural: put retrieval behind an interface from the start so the store is swappable, and write the golden-set evaluation early so the migration can be verified rather than hoped for.

**On testing:** an in-memory Chroma collection in a test suite gives fast, deterministic retrieval tests without network calls or a running service. That's a legitimate permanent use in a production codebase even when serving runs on Vertex AI Vector Search — with the caveat that tests should use fixed, precomputed embeddings so they don't depend on a model call.

## 8. Likely Follow-ups

**Q: When would you use Chroma?**
Prototyping, learning, notebooks, small internal tools, and test suites. The in-memory collection is genuinely useful for hermetic retrieval tests in a production codebase, even when serving happens on something else entirely.

**Q: What's the risk with auto-embedding?**
It silently picks a default model, so the component that most determines retrieval quality wasn't chosen by you. Results measured in the prototype — chunking comparisons, threshold values, recall numbers — may not transfer to production with a different embedding model. Passing embeddings explicitly avoids it.

**Q: Why not use Chroma in production?**
It's not built for concurrency, doesn't scale much past a million vectors, and has no replication, HA, or serious access control. For a small internal tool that's fine; for a customer-facing banking system it isn't the right shape.

**Q: How do you stop a prototype becoming production?**
Architecturally, not by policy. Put retrieval behind an interface from the start so the store is swappable, and build the golden-set evaluation early so a migration can be verified. Both are cheap on day one and expensive to retrofit after the prototype has users.

**Q: Is there a permanent place for it in a production codebase?**
Yes — tests. An in-memory collection gives fast deterministic retrieval tests with no service dependency. I'd use fixed precomputed embeddings so the tests don't call a model, which keeps them hermetic and fast.

## 9. Common Mistakes

- Relying on auto-embedding and assuming results transfer to production.
- Benchmarking chunking strategies on a different model than production will use.
- Letting a prototype become the production system by default.
- Using it for concurrent multi-writer serving.
- Not putting retrieval behind an interface from the start.

## 10. What to Remember

- **The fastest path to working retrieval** — zero configuration, embedded.
- **Auto-embedding hides the model**, which invalidates prototype comparisons.
- **Pass explicit embeddings from the production model**, even in prototypes.
- **In-memory collections are genuinely good for tests.**
- **Guard against prototype-becomes-production** with an interface and early evals.
