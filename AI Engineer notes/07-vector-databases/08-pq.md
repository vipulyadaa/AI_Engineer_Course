# PQ (Product Quantization)

> **Phase 07 · VECTOR DATABASES · Topic 08**

## 1. Definition

A compression technique that splits each vector into sub-vectors, replaces each sub-vector with the ID of its nearest centroid from a small learned codebook, and stores only those IDs. It reduces memory by 10–100× at the cost of approximate distances.

## 2. Simple Explanation

Instead of storing 768 floating-point numbers per vector, split them into chunks, learn 256 representative patterns for each chunk position, and store which pattern each chunk is closest to.

A 768-dimensional vector becomes a handful of bytes. Distances are then computed against the representative patterns rather than the originals — approximate, but fast and tiny.

## 3. How It Works

```
Original: 768 dims × 4 bytes = 3,072 bytes

1. SPLIT into m = 96 sub-vectors of 8 dims each
2. TRAIN a codebook per sub-vector position:
       k-means with 256 centroids over that slice
3. ENCODE each sub-vector as its nearest centroid ID (1 byte)

Compressed: 96 bytes  →  32× smaller

DISTANCE (asymmetric — the important variant):
  · keep the QUERY uncompressed
  · precompute a 96 × 256 table of query-slice-to-centroid
    distances — one small table per query
  · a vector's distance = sum of 96 table lookups

No multiplication at all. Just adds. This is why PQ is fast
as well as small.
```

**Asymmetric distance computation (ADC)** — comparing an uncompressed query against compressed vectors — is notably more accurate than compressing the query too, and costs nothing extra. It's the default in practice.

## 4. Practical Example

**Why billion-scale needs it:**

```
1,000,000,000 vectors × 768 dims × 4 bytes  = 3.07 TB
With PQ at 96 bytes                          = 96 GB

3 TB doesn't fit in RAM on anything reasonable.
96 GB fits on one large machine.

That's the entire argument for PQ. It's not a speed
optimization — it's what makes the corpus fit at all.
```

**The recall cost is real:**

```
Typical, at billion scale:

  Flat (exact)        recall 1.00     3 TB
  IVF                 recall ~0.95    3 TB
  IVF-PQ (m=96)       recall ~0.80    96 GB
  IVF-PQ (m=192)      recall ~0.88    192 GB

PQ trades 10-20 points of recall for 32× memory.
That's a bad trade UNLESS the alternative is not fitting.
```

**The standard mitigation — rerank with full vectors:**

```
1. PQ search over the compressed index → top-200 candidates
2. Fetch the FULL vectors for those 200 (from disk/SSD)
3. Rescore exactly → top-10

Recovers most of the lost recall for 200 disk reads.
This two-stage pattern is why IVF-PQ is usable in production
rather than just memory-efficient.
```

**Note this is a different reranking from a cross-encoder** — here it's exact vector distance recovery, not semantic relevance scoring. Both can be in the same pipeline.

## 5. Why It Matters

- **It's what makes billion-scale search fit in memory** — the argument is capacity, not speed.
- **Asymmetric distance computation** turns distance into table lookups with no multiplications.
- **The rerank-with-full-vectors pattern** is what makes the recall cost acceptable.

## 6. Trade-offs / Failure Modes

| Issue | Detail |
|---|---|
| **Significant recall loss** | 10–20 points versus uncompressed |
| **Requires training** | Codebooks learned from a representative sample |
| **Distribution shift breaks codebooks** | Centroids stop representing the data |
| **Distances are not comparable to uncompressed** | Thresholds must be recalibrated |
| **Used prematurely** | At 5M vectors, PQ's recall cost buys nothing you need |
| **No full vectors retained** | Can't rerank; recall loss becomes permanent |

**On premature use — the most common mistake:** PQ exists for corpora that don't fit in RAM. At five or ten million vectors, raw vectors are 15–30 GB, which fits on an ordinary machine. Applying PQ there gives up 15 points of recall to save memory you weren't short of.

**On retaining full vectors:** the rerank stage needs them, so they have to live somewhere — object storage or SSD. A design that discards originals after encoding locks in the recall loss permanently, and also makes any future re-encoding impossible.

## 8. Likely Follow-ups

**Q: How does PQ compress?**
It splits each vector into m sub-vectors, learns a codebook of 256 centroids per sub-vector position via k-means, and stores each sub-vector as a one-byte centroid ID. 768 dimensions in ninety-six slices goes from three thousand bytes to ninety-six — about thirty-two times smaller.

**Q: What is asymmetric distance computation?**
Keeping the query uncompressed while the stored vectors are compressed. You precompute a table of distances from each query slice to each codebook centroid, then each vector's distance is a sum of table lookups with no multiplications. It's both faster and more accurate than compressing the query as well.

**Q: What does PQ cost you?**
Typically ten to twenty points of recall. That's acceptable only when the alternative is the corpus not fitting in memory — which is the actual reason to use it. The standard mitigation is reranking the top candidates against full uncompressed vectors fetched from disk.

**Q: When would you not use PQ?**
Whenever the raw vectors fit comfortably in RAM. At five or ten million vectors that's fifteen to thirty gigabytes on an ordinary machine, so PQ would trade real recall for memory you weren't short of. It's a billion-scale tool.

**Q: How do you recover the lost recall?**
Two-stage retrieval: PQ search over the compressed index to get a few hundred candidates, then fetch their full vectors from SSD or object storage and rescore exactly. That recovers most of the loss for a few hundred disk reads, which requires having kept the originals somewhere.

## 9. Common Mistakes

- Using PQ when the corpus fits in memory anyway.
- Discarding full vectors after encoding, making the recall loss permanent.
- Comparing PQ distances against thresholds calibrated on uncompressed vectors.
- Not retraining codebooks after significant distribution shift.
- Describing PQ as a speed optimization rather than a capacity one.

## 10. What to Remember

- **Split, learn a codebook per slice, store centroid IDs** — 32× smaller typical.
- **Asymmetric distance:** uncompressed query, table lookups, no multiplications.
- **The reason is capacity** — 3 TB → 96 GB at billion scale.
- **Costs 10–20 points of recall**; rerank against full vectors to recover most of it.
- **Don't use it if the vectors already fit in RAM.**
